# Prior art for code tours

Research for [#3](https://github.com/saiashirwad/slick-annotate/issues/3), feeding the Tours design work tracked in [#1](https://github.com/saiashirwad/slick-annotate/issues/1).

## Takeaways: copy / avoid

**Copy**

- **A tour is a linear list of steps, each anchored to a file/line/directory, with markdown prose.** Every tool converges on this shape — CodeTour's `.tour` JSON ([schema](https://github.com/microsoft/codetour#tour-schema)), Swimm's `.pl.sw.md` playlists, Sourcegraph's Diff Tour sections. Don't invent a richer model.
- **Anchor by line *and* a resilience fallback**, not line number alone. CodeTour supports `line` or a regex `pattern` match ([README](https://github.com/microsoft/codetour#tour-schema)); Swimm's auto-sync scores line markers, tokens, and file history to re-anchor snippets after edits ([Swimm blog](https://swimm.io/blog/how-does-swimm-s-auto-sync-feature-work)). Pure line numbers rot the moment code shifts.
- **Store tours as plain files in the repo, human-editable, git-diffable.** CodeTour: JSON under `.tours/` ([README](https://github.com/microsoft/codetour#tour-files)). Swimm: markdown under a docs folder, explicitly chosen so playlists "can easily be edited within your IDE or reviewed in Pull Requests" ([Swimm docs](https://docs.swimm.io/features/swimm-playlists/)). Don't put tour state in an opaque DB or SaaS silo.
- **Reuse VS Code's Comments API for the step UI** — the same primitive Slick Annotate already uses for annotations. CodeTour's player builds its step bubble on `vscode.comments.createCommentController`, with Previous/Next/Edit/End actions in the same comment thread widget ([`src/player/index.ts`](https://github.com/microsoft/codetour/blob/main/src/player/index.ts)). This is the direct "copy" for staying native-UI-only.
- **Track progress so a tour can be paused and resumed**, not just played start-to-finish in one sitting. Swimm remembers "where you've left off" per playlist ([Swimm docs](https://docs.swimm.io/features/swimm-playlists/)); CodeTour got repeated requests for this exact thing when it lacked it (see "avoid" below).
- **Let a step reference other steps/tours**, cheaply, as markdown links. CodeTour's step/tour cross-references (`[#2]`, `[Tour Title]`) and command-links (`command:` scheme) cost nothing extra once you're rendering markdown anyway ([README](https://github.com/microsoft/codetour#step-references)).

**Avoid**

- **Don't make drift-repair a manual, out-of-scope afterthought.** CodeTour's maintainer's stance is explicit: *"Auto-updating a tour is outside the scope of this extension unfortunately"* ([issue #296](https://github.com/microsoft/codetour/issues/296)), which pushed teams to build their own external re-anchoring scripts (e.g. [RocketChat/RC.Guided.Tours](https://github.com/RocketChat/RC.Guided.Tours), referenced in the same thread). For an agent-authored tour, the agent that wrote the tour is the cheapest thing available to re-anchor it — don't defer that to the user.
- **Don't let tours go stale as a maintenance burden with no owner.** CodeTour itself shows the failure mode: last release `v0.0.59` was March 2023 despite the repo staying open, and users are asking *"还有人维护吗？"* ("is anyone still maintaining this?") in [issue #331](https://github.com/microsoft/codetour/issues/331) as recently as 2026. A tour format that requires hand-maintenance decays.
- **Don't ship a step player with real bugs in the basics** — CodeTour has long-open reports of the "Insert Code" action not appearing ([#150](https://github.com/microsoft/codetour/issues/150)), a directory step's Explorer view breaking until reload ([#62](https://github.com/microsoft/codetour/issues/62)), and a VS Code update silently capping the comment bubble's height ([#285](https://github.com/microsoft/codetour/issues/285)). Native-UI extensions are exposed to host UI changes; keep the surface area small enough to actually keep working.
- **Don't force one linear path through with no resume state.** Before it was fixed, CodeTour had no way to jump back to where a presentation left off after navigating away ([#102](https://github.com/microsoft/codetour/issues/102)) — a real complaint for anything longer than a few steps.
- **Don't stop at ephemeral chat as "the tour."** Copilot's own "explore a codebase" guidance and Cursor's code-understanding docs are both, by their own description, just Q&A in a chat pane: "type a question in the prompt box... and press Enter" ([GitHub Docs](https://docs.github.com/en/copilot/tutorials/explore-a-codebase)); Cursor "maintains context within a conversation, so you can start broad and drill into specifics with follow-up questions" ([cursor.com/for/code-understanding](https://cursor.com/for/code-understanding)). Nothing persists, nothing is re-walkable by someone else, nothing lands as a file. That's the gap a checked-in, native-UI Tour artifact actually fills — don't accidentally rebuild a chat transcript.
- **Don't overreach into voice/animation gimmicks as the interaction model.** At least one community MCP server drives CodeTour with text-to-speech narration and playback-speed controls ([benstaniford/CodeTour on Glama](https://glama.ai/mcp/servers/benstaniford/CodeTour)); another ("mcp-walkthrough") narrates steps with a synced "teleprompter" bubble via global keyboard shortcuts ([stefan-nitu/mcp-walkthrough](https://github.com/stefan-nitu/mcp-walkthrough)). Fun demos, but they add a whole media/audio layer to what should stay a quiet, native, keyboard-driven reading experience — same instinct as this project's own settings/theme/export minimalism.
- **Do let the agent write the tour, but keep the tool "dumb" (validate + persist only).** The one in-flight proposal to let an agent author CodeTour content explicitly keeps content generation on the agent side and limits the MCP server to schema/anchor validation and atomic file writes ([microsoft/codetour#336](https://github.com/microsoft/codetour/issues/336), implementation in [PR #338](https://github.com/microsoft/codetour/pull/338), still open/unmerged as of 2026-09-27). That split (agent writes prose + picks anchors; tool only validates and persists deterministically) is the right shape to copy for an MCP-driven Tour writer here.

## Microsoft CodeTour

Source: [microsoft/codetour](https://github.com/microsoft/codetour) (README, `package.json`, and `src/` read directly from the repo; 4.6k stars, MIT).

**What a tour is made of.** A tour is a JSON file (schema documented in the [README](https://github.com/microsoft/codetour#tour-schema)) with a `title`, optional `description`/`ref`/`isPrimary`/`nextTour`/`when`, and an ordered `steps` array. Each step has a `description` (markdown), and is anchored by exactly one of `file`+`line`, `file`+`pattern` (regex, used when the tour should survive line-number drift), `directory`, or `uri`; steps can also be pure "content steps" (title + markdown, no code anchor) for intros/interludes. "CodeTour-flavored markdown" adds file/step/tour cross-links, `>>`-prefixed shell-command links, "Insert Code" buttons on fenced code blocks, and arbitrary `command:` links to any VS Code command.

**Storage.** Tours live as `.tour` JSON files under `.tours/` (or `.vscode/tours`, `.github/tours`, or a single `.tour`/`main.tour`) in the workspace — checked into git by default — or can be "exported" to a standalone file (with file contents embedded) for sharing outside the repo, including to a GitHub Gist via the GistPad extension.

**Navigation.** Linear Previous/Next/Edit/End actions live in the step's comment-thread UI. Tours can be chained (`nextTour`, or numeric title prefixes like `1 - Foo`) so "Finish Tour" becomes "Next Tour" across a series. A "primary tour" is auto-suggested on first workspace open. Gutter "tour markers" surface on lines that participate in a tour, with a hover "Start Tour" link.

**Interaction.** Read-only by default; if the tour's git ref matches the user's checked-out state, files stay editable while a tour plays. Versioning is done by pinning steps to `None` / current branch / a specific commit / a tag, traded off against tour resilience to code changes.

**VS Code APIs used** (confirmed by reading `src/`): `vscode.comments.createCommentController` for the step bubble UI ([`src/player/index.ts`](https://github.com/microsoft/codetour/blob/main/src/player/index.ts)) — the same Comments API Slick Annotate uses for annotations; a custom `TreeDataProvider` for the "CodeTour" Explorer view ([`src/player/tree/index.ts`](https://github.com/microsoft/codetour/blob/main/src/player/tree/index.ts)); a `FileSystemProvider` to render virtual documents for directory/content steps ([`src/player/fileSystem/index.ts`](https://github.com/microsoft/codetour/blob/main/src/player/fileSystem/index.ts)); editor gutter decorations for tour markers (`src/player/decorator.ts`). No webviews for the core playback UI.

**Known complaints** (from the [issue tracker](https://github.com/microsoft/codetour/issues), read directly): drift ("auto update with changing codebase" is explicitly out of scope per the maintainer, [#296](https://github.com/microsoft/codetour/issues/296)); maintenance concerns — last release `v0.0.59` shipped 2023-03-24, most recent commit as of this research is 2025-08-07, and users ask if it's still maintained ([#331](https://github.com/microsoft/codetour/issues/331)); UI bugs in "Insert Code" not appearing ([#150](https://github.com/microsoft/codetour/issues/150)), a directory step breaking the Explorer view until reload ([#62](https://github.com/microsoft/codetour/issues/62)), and a VS Code update capping the step bubble's max-height ([#285](https://github.com/microsoft/codetour/issues/285)); missing resume-after-navigating-away before it was addressed ([#102](https://github.com/microsoft/codetour/issues/102)); and a live, unmerged proposal + PR to add an MCP server so agents can author tours directly ([#336](https://github.com/microsoft/codetour/issues/336) / [PR #338](https://github.com/microsoft/codetour/pull/338)) — i.e., the exact gap this project's own Tours feature would fill, independently identified by a third party against CodeTour itself.

## AI-era equivalents

### Sourcegraph "Diff Tour"

Source: [sourcegraph.com/docs/diff-tour](https://sourcegraph.com/docs/diff-tour). Generates a reading path over a *diff*, not a whole codebase: it "places important files first, groups related files into sections, and explains the diff, each section, and individual files." Consumption is passive and linear — "read the tour from top to bottom," marking files viewed as you go — with no mechanism described for asking follow-up questions. Generated once per diff and cached so other reviewers of the same diff reuse it; reached from a repo's Compare page, Branches tab, or a commit page (GitHub users need the Sourcegraph browser extension). Currently beta, not on Sourcegraph.com, requires accepting Sourcegraph's AI terms. Relevant mainly as a narrower "explain this change" sibling to a full codebase tour, and as prior art for caching an LLM-generated explanation so it doesn't regenerate per viewer.

### Swimm

Source: [Swimm docs](https://docs.swimm.io/features/swimm-playlists/) and [Swimm engineering blog](https://swimm.io/blog/how-does-swimm-s-auto-sync-feature-work). A **Playlist** is an ordered collection of Swimm docs, links, videos, and images, authored via a point-and-click web/IDE editor, stored as human-readable markdown (`.pl.sw.md`) inside a Swimm docs folder in the repo — git-tracked, diffable, reviewable in PRs. Individual docs embed live code snippets; Swimm's **auto-sync** re-anchors a snippet after the underlying code changes using a scoring model over "line markers, line numbers, token references, size of the change, [and] history of the file in version control" rather than trusting a stored line number. Consumption tracks read/unread progress per user so a playlist can be paused and resumed. Swimm is closed-source SaaS with no public issue tracker, so complaint data is thinner than CodeTour's; secondary aggregator sources (G2-derived, e.g. [thectoclub.com](https://thectoclub.com/tools/swimm-review/)) report the IDE plugin as the weakest part of the product and pricing as a barrier for smaller teams — treat this as low-confidence, secondary-sourced. The auto-sync approach (multi-signal re-anchoring, not just line numbers) is the most transferable idea here.

### Greptile (formerly "Onboard")

Source: reported via secondary coverage (no first-party "Onboard" history page was found still live). Greptile began in mid-2023 as a hackathon project under the name **Onboard** / Onboard AI, explicitly framed as letting developers "talk" to their codebase to onboard onto unfamiliar code; it has since repositioned entirely as an AI code-review tool for GitHub/GitLab PRs. There is no current standalone "tour" artifact or feature to evaluate — it's chat-driven Q&A grounded in a codebase index, same category as Copilot/Cursor chat below, not a structured, replayable tour.

### GitHub Copilot and Cursor "explain codebase" features

Sources: [GitHub Docs — "Using GitHub Copilot to explore a codebase"](https://docs.github.com/en/copilot/tutorials/explore-a-codebase) and [cursor.com/for/code-understanding](https://cursor.com/for/code-understanding), both read directly. Both are **chat Q&A, not a tour artifact**: Copilot's own tutorial frames exploration as asking progressively narrower questions ("Ask a follow-up question to go deeper, using the same shared context") with no persistent, step-ordered output. Cursor's docs describe the same pattern — "start broad and drill into specifics with follow-up questions" — and its only durable artifact is a manual one: the user copies things they learned into `.cursor/rules/` files for future sessions. Cursor can render Mermaid diagrams inline for architecture explanations, but these live in the chat transcript, not as a separate, navigable, shareable file. Neither tool produces a checked-in, re-walkable, line-anchored artifact — this is the clearest gap versus CodeTour/Swimm, and the one a native VS Code Tour (backed by the Comments API, like this extension's annotations) would fill for agent-driven explanations.

### Agent-generated tour tools / MCP servers for tours

Three concrete, independent efforts were found building an agent-facing layer on top of (or instead of) CodeTour, all recent (Sept 2026):

- **[microsoft/codetour#336](https://github.com/microsoft/codetour/issues/336)** (open proposal) + **[PR #338](https://github.com/microsoft/codetour/pull/338)** (open, unmerged, from the same author): a local MCP server bundled with CodeTour exposing `create_project_tour` and `create_changes_tour`. The agent supplies fully-written step content; the server's only job is validation (schema, anchor bounds checked against real file content, rejecting active URI schemes like `command:`/`javascript:` in markdown, regex-pattern length/backtracking limits, git refs resolved to full SHAs) and atomic, deterministic writes of `.tour` files. Explicit design goal: "the agent provides fully written content; the server only validates and persists it... keeps the human in charge of the narrative." Runs over stdio, confined to a `--workspace-root` argument, no network access.
- **[stefan-nitu/mcp-walkthrough](https://github.com/stefan-nitu/mcp-walkthrough)**: an independent MCP server (not CodeTour-based) that drives VS Code directly — opens files, highlights line ranges, shows markdown, and narrates steps with text-to-speech. Steps are plain JSON (`file`, `line`/`endLine`, `title`, `explanation`, `highlights[]` with per-line narration) passed at call time, not saved as a repo artifact. Navigation is global keyboard shortcuts (`Cmd+Shift+→/←/↓`) with an animated "teleprompter" bubble.
- **[benstaniford/CodeTour MCP server](https://glama.ai/mcp/servers/benstaniford/CodeTour)**: wraps GitHub PRs specifically — pulls PR metadata/diffs via the GitHub API and drives an "explain like I'm five" narrated tour (7 tools: `get_pr_info`, `get_file_diff`, `start_tour`, `show_overview`, `show_step`, `end_tour`, `tour_status`) in a browser viewer with synced text-to-speech captions, pausable/resumable, adjustable pace and voice.

Common thread: all three treat the LLM/agent as the author of tour *content* and keep the tool itself to mechanical anchoring + playback, matching this project's own instinct to keep the extension thin. The two non-CodeTour servers both reach for voice narration and animation as the interaction model — worth noting as a road not to take for a "slick, native-UI" tour (see Avoid, above).
